# PRD：Windows 设置开关可靠性迭代

## 1. 背景

zipax 的 Windows 客户端在“通用”设置中存在开关可见但无法点击的问题，已明确影响：

- 开机自动启动；
- 自动更新检查。

同一套 `HeroSwitch` 封装还被工作流、自动化和压缩设置复用，因此问题具有横向扩散风险。

## 2. 问题定义

项目升级到 HeroUI v3 后，开关封装仍按旧的组件结构使用 `Switch.Control`。v3 的交互元素由 `Switch.Content` 提供，当前 DOM 只有视觉轨道，没有实际的可点击 `SwitchButton`，导致鼠标、键盘均无法切换。

Windows 使用 `zipax-cross` 的 Tauri/React 界面；macOS 主客户端使用 SwiftUI，因此该问题主要暴露在 Windows 版本。

开机启动还有一项可靠性缺口：界面提交系统设置期间没有忙碌状态，也没有在写入后回读系统真实状态，失败或快速重复点击时可能出现 UI 与系统注册状态不一致。

## 3. 目标

- Windows 下开机启动与自动更新开关可以通过鼠标和键盘正常切换。
- 所有复用 `HeroSwitch` 的设置恢复交互，避免同类问题继续扩散。
- 每个无文本开关都有可访问名称。
- 开机启动提交期间禁止重复操作，完成后以系统回读结果为准。
- 自动更新开关继续写入 Zustand 持久化状态，重启应用后保持用户选择。

## 4. 非目标

- 本次不修改更新清单、签名、下载和安装链路。
- 本次不改变 Windows 注册表中的开机启动实现。
- 本次不重做设置页视觉设计。
- 本次不调整 macOS SwiftUI 客户端。

## 5. 方案与迭代计划

### Phase 0：交互热修复（本次实施）

1. 按 HeroUI v3 结构，用 `Switch.Content` 包裹轨道、滑块和可选标签。
2. 将 `ariaLabel` 设为 `HeroSwitch` 的必填属性，并补齐全部调用点。
3. 开机启动写入期间禁用开关，成功后回读系统状态；失败时回滚 UI。

### Phase 1：状态反馈与自动化测试

1. 为系统设置写入失败增加页面内错误提示，而不只记录控制台警告。
2. 增加 `HeroSwitch` 组件测试：鼠标点击、Space/Enter、受控值变化、禁用态。
3. 增加设置持久化测试：自动更新开关切换后重新初始化 Store，状态不丢失。

### Phase 2：平台能力收敛

1. 评估把自定义 `auto-launch` 命令统一到已接入的 Tauri autostart 插件。
2. 建立 Windows 10/11、安装版/便携运行、标准用户/管理员的验证矩阵。
3. 为 updater 增加 Windows 发布产物的端到端检查，包括清单、签名、下载与重启安装。

## 6. 验收标准

- 点击“开机自启”后开关立即响应，写入期间不可重复点击，最终状态与系统回读一致。
- 点击“自动更新”后开关立即响应，关闭并重新打开应用后状态保持。
- Tab 可聚焦开关，Space 可切换；读屏软件能读出设置名称和开关状态。
- 其他复用开关（后台运行、工作流、自动化、压缩选项）均可正常切换。
- TypeScript 和 Vite 生产构建通过。

## 7. 风险与回滚

- `HeroSwitch` 是共享组件，修改会影响多个页面；通过补齐所有调用点并执行生产构建降低风险。
- 系统开机启动写入仍可能因环境策略失败；当前会回滚到原值，Phase 1 再补充可见错误提示。
- 如出现 UI 回归，可单独回滚 `HeroSwitch` 结构和调用点，不涉及用户数据迁移。
